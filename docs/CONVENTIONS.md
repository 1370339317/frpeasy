# 改代码前必须知道的硬约束

这些不是风格偏好,是踩过坑之后定下来的。每一条都对应一个「改错了会静默失败、
而且现象看起来完全像别的原因」的场景。改之前先读完,改完跑一遍对应测试。

---

## A. 版本与发布

### A1. 面板是唯一的版本源

客户端只从 `/api/agent/bin/{os}/{arch}` 取二进制,**永不直连 GitHub**。
所以「面板自带哪一版 agent」才是权威,`manifest.json` 里的 agent 资产只用于提示。

改这里会导致:内网机器明明能连面板,却因为尝试访问 GitHub 而升级失败。

### A2. 发布前必须 `make check-manifest`

清单里的 sha256 一旦与产物不符,客户端会校验失败拒装 —— 现象是
**「升级一直失败」而面板侧完全正常**(清单版本比客户端新,于是不停下发)。

`make build` 里的 `stage-local` 会把本机 agent 覆盖进 `bin/` 而同平台的旧清单
不更新,这是最常见的失配来源。上传前养成习惯:

```bash
make manifest VERSION=x.y.z && make check-manifest
```

所有 `go build` 都带 `-trimpath`,保证同一源码在不同目录构建出字节相同的产物。

### A3. 更新源的初始值来自 `FRPEASY_UPDATE_BASE`,但只在 DB 里该值为空时生效

`update_base` 为空串的语义是「不检查更新」,所以一键部署脚本靠这个环境变量
把面板接到 Release 上;**而用户在设置页手改过之后,DB 里有值,重启不再覆盖他**。

这条链断了不会报错,只会表现为「点检查更新什么都不发生」。
`deploy.sh` 写进 unit 的 `Environment=FRPEASY_UPDATE_BASE=...` 就是为了接上它。

## B. 自更新

### B1. 面板自我替换不能自己重启自己

旧进程先把自己复制成 handoff 副本,由副本等旧 PID 退出、换文件、拉起、
再比对 `version` 字段确认成功,失败则回滚 `.prev`。

**健康检查必须比对 `version` 字段**,只判 HTTP 200 会把「旧进程还没退干净」
当成成功 —— 于是报告升级成功,实际还是旧版本在跑。

### B2. systemd 托管时,交接器必须用 `systemctl` 启停,不能自己 spawn

配套的 unit 必须是 `Restart=on-failure` + `KillMode=process`,三处缺一不可:

- **`on-failure`**:面板交接时 exit 0 主动退出,systemd 认为正常退出不重启,
  给交接器一段干净的时间换文件。用 `always` 会和交接器抢端口,更坏的情况是
  旧版抢先占住端口,交接器把新版本的启动失败误判成「新版本有问题」而回滚 ——
  **升级永远升不上去,日志还会说是新版本的错**。
- **`KillMode=process`**:交接器是面板的子进程、同一 cgroup,默认策略会在服务
  停止时把它一起清掉 —— 正好在「面板已退出、交接器要换文件」这个最脆弱的时刻。
- **交接器自己 `spawn` 也不行**:起来的进程不在 unit 的 cgroup 里,
  `systemctl status/stop` 管不到,下次重启就两份进程抢端口。

`startTarget` / `stopTarget` 与三个测试守着这条。unit 模板只有一份:
`scripts/frpeasy.service`(`deploy.sh` 从更新源拉的就是它,绿色包里那份是同一文件的渲染结果)。

### B3. 二进制查找顺序固定:面板同级 → 同级 `bin/` → `<data>/bin`

改这里会导致「装的时候能下、升级时 404」。

### B4. 面板更新成功后,页面必须自己重新加载

换的是**二进制**,而已经打开的标签页不会重新拉 `index.html` —— 内存里跑的
还是更新前那份 JS。如果不主动刷新,用户会看到「更新成功」却在界面上找不到
新功能(典型反馈:「左侧怎么没有某某菜单」),而且换台设备又是对的,极难自查。

两道保险,缺一不可:

- **更新成功当场刷**:`VersionCard` 收到 `stage=succeeded` 后延迟 1.2 秒
  `location.reload()`;
- **过期自愈**:`GET /api/ui/build` 返回当前 `index.html` 引用的入口脚本名
  (Vite 产物带内容哈希),前端拿 `import.meta.url` 里的自己的名字跟它比,
  不一致就提示并刷新(`web/src/lib/uidrift.ts`)。这一条覆盖「别人升级了面板」
  「标签页在后台放了很久」等所有更新当场刷不到的场景。

判据用**入口文件名**而不是版本号:版本号不同可能只是后端改动,文件名不同
必然是前端产物换了。开发态(`vite dev`,入口是 `/src/main.tsx`)不参与比较。

## C. 网络与端口

### C1. 面板对外地址一律走 `resolvePanelBase(r)` / `resolveFRPSAddr(r, port)`

禁止直接读 `public_addr`。该值默认为空,直接用会生成 `<你的服务器IP>` 这种
复制到终端就报错的占位符,或者 `FRPSAddr` 是空串导致 frpc 连不上。

优先级:设置项 → 请求 Host(采信 `X-Forwarded-Proto` / `r.TLS`)→ `127.0.0.1:<listenPort>`。

### C2. frp ≥ 0.52 的 TOML 必须是新版顶层驼峰键

```
frps:  bindPort / auth.method / auth.token
frpc:  serverAddr / serverPort / auth.* / [[proxies]]
```

不能沿用旧 INI 的 `[common]` / `server_addr` / `remote_port`。有测试守着
(断言生成的配置里不出现这些旧键)。

### C3. 端口池默认 21000–26000,frps bindPort 默认 27900,dashboard 默认 27500

dashboard **只监听 127.0.0.1**,是面板读取真实代理状态的通道,不对外暴露,
也不需要放行。端口清单的唯一来源是 `ports.go`,文档里不要另抄一份。

---

### C4. 客户端侧的 host:port 必须在入库前校验

隧道记录里的 `local_addr` 会被原样写进客户端的 `frpc.toml`（`localIP` / `localPort`）。
端口写成 `99999`、`0`、`abc` 时 frpc **解析失败直接退出**，而同一台客户端上所有
隧道共用这一个 frpc 进程 —— 一条写坏的记录会把那台机器上全部隧道一起拖下线，
面板上只看到"全都离线"，指不出是哪一条的错。实测（0.7.24 线上 + Windows 客户端）：
`PUT local_addr=127.0.0.1:99999` 被接受，25 秒后 frpc 进程消失、该机隧道全部 offline。

所以 `CreateTunnel` / `UpdateTunnel` 都要过 `normalizeLocalAddr`：host 非空、
端口是 1-65535 的**纯数字**。只判"能不能用"，不判"通不通"—— 本地服务没起来是另一回事，
frpc 会报 connection refused，界面上看得到，也不影响别的隧道。

**必须返回规范形式并落库**，不能只报错。0.7.26 实测这三种都能通过校验并原样入库：
`127.0.0.1: 80`（冒号后带空格）、`127.0.0.1:081`（前导零）、`127.0.0.1:+80`。
客户端靠 `Sscanf` 宽容解析才没出事，但面板列表显示的是那串脏值 —— 用户看到
`本地服务 127.0.0.1:081` 只会怀疑配置写坏了。规范化同时挡掉 `256.256.256.256:80`
（像 IPv4 就必须是合法 IPv4，否则 frpc 每次拨号都失败、隧道永远连不上）。

**隧道名称有硬上限（64 个字符）且不许控制字符**。名字是列表里唯一"用户能写多长
就多长"的列：0.7.26 实测 200 个字符的名字把名称列撑到 1473px、整表 2210px，
而视口 1440px —— 公网地址、状态、编辑/删除全被推出屏幕，**一条脏名字毁掉整个列表**。
服务端限长是必须的（API 不经过 UI），前端截断是第二道（列宽由界面决定，不由数据决定），
两道都要，缺任何一道都能复现。

同理，隧道名称要 `TrimSpace` 后再判空：只填空格会让列表里出现一行没有名字的记录。

### C5. 登录失败必须限速

面板在公网上等于把 frps 的控制面暴露出去，而 admin 口令常是初始值。
线上实测（0.7.24）：连续 20 次错误口令全部 401，没有延迟、没有封禁 —— 字典随便跑。

`loginGuard`（`auth.go`，内存表）：同一来源 10 分钟内错 8 次 → 封 5 分钟，
再错翻倍（上限 60 分钟），成功一次清零；封禁期返回 429 + `Retry-After`。
**按来源 IP 记账**，且只在可信对端（环回/内网，即反代）时才采信
`X-Forwarded-For` —— 否则一个人爆破会把所有访客（包括站主自己）一起锁住。

### C6. 客户端必须自己留日志

Windows 上 agent 由**计划任务**启动，stdout/stderr 没有人接收。0.7.26 之前的后果是：
安装目录里只有 `agent.state` 和二进制，`frpc` 退出/重启这类问题**没有任何证据**
（一次并发压测里 frpc 进程重启，事后完全无法归因；面板侧也只有 frps 日志）。

现在 `SetupFileLog` 在 `NewClient` **之前**就把 `log` 接到 `<data>/agent.log`
（4MB 滚动成 `.1`，总量上限约 8MB，`io.MultiWriter` 保留 stderr）——
连不上面板、注册被拒这些启动期故障恰恰最需要证据，而它们全发生在 `Run()` 之前。
frpc 的 stdout/stderr 经 `lineLogger` 按行转成 `[frpc] ...` 进同一份日志，
进程退出时 `Flush()` 把最后半行（通常就是报错本身）冲出去。
运行期诊断（心跳失败、配置拉取失败、重新注册）一律 `log` 而不是 `fmt.Println`，
后者在计划任务下等于丢进黑洞。

**日志回传通道**（0.7.29 起）：面板读不到客户端本地文件，也连不上 NAT 后面的机器，
所以是「面板请求 → 客户端下一次配置轮询时回传」：

- `POST /api/agents/{id}/logs` 只写一个请求 ID（`agent_logs.request_id`），不算回传；
- 请求随 `AgentConfig.LogRequest` 下发（与卸载同一条必经通道）；
- 客户端**只在 ID 变化时**回传一次（`lastLogReq` 去重），回传后服务端立刻清空请求 ——
  不去重就是每 15 秒上传一份同样的 64KB；
- 回传带 agent_token（日志里有内部地址与报错原文，不能凭猜到的请求 ID 写入）；
- 客户端只传尾部 64KB 且**从行边界开始**（半个时间戳开头的首行会让人以为日志坏了）；
- 界面上三种状态必须分开：等回传 / 已回传本次 / 超时且只有上一次的旧快照。
  第三种最容易骗人 —— 把旧内容当本次结果展示，用户会以为客户端刚才传了。
- 版本门槛只拦「确实是旧版」：版本号认不出来（`dev`、本地构建）放行，
  否则会给出「版本 dev 低于 0.7.29」这种荒唐提示（`shared.VersionKnown`）。

## D. 前端与构建

### D1. 前端产物不入库,但必须 embed

链路:`web/src` → Vite → `internal/webui/dist` → `go:embed`。

`vite.config.ts` 里的 `base: './'` **不能改成 `/`** —— 面板可能挂在反代子路径下,
绝对路径会 404。有测试守着。

`internal/webui/dist/.keep` 必须入库:真实产物不入库,缺了它干净 clone 编不过
(`go:embed all:dist` 无匹配)。

缓存策略:`/assets/*` immutable 长缓存,`index.html` 强制 `no-store`
(否则升级后仍显示旧页)。

### D2. 类型双写

Go 结构体与 `web/src/types.ts` 必须逐字对齐,没有编译期约束。改一个就要改另一个。

### D3. 导航按「在干什么」分三组,新增页面必须先归组

`web/src/views.ts` 的 `VIEW_GROUPS` 是唯一来源(标题、hash 路由都从它派生):

| 组 | 页面 | 判据 |
|---|---|---|
| 组建隧道 | 概览 / 隧道 / 客户端 | 决定「暴露什么、给谁用」 |
| 这台服务器 | frps 服务端 / 端口与防火墙 / 文件与更新 | 这台机器在跑什么、有哪些文件、要开哪些口 |
| 系统 | 设置 | 口令、公网地址、下载源、端口池 |

两条硬规矩:

- **同一类东西必须落在同一组**:版本与更新原来在「设置」、托管文件在另一页,
  同一件事被拆成两处,用户根本不知道该去哪看。现在合为「文件与更新」。
- **不要再往顶层平铺**:条目只会越来越多,平铺后「找东西要通读一遍」。
  新增页面前先答「它属于哪一组」;答不出来说明页面职责没想清。

`nav` 必须可滚动(`overflow-y-auto`):窗口不高时不能把下面的组挤出屏幕 ——
表现就是用户报「菜单怎么不见了」。

## E. 下发的脚本

`internal/panel/scripts/*.sh|*.ps1` 的换行符**必须是 LF**,由 `.gitattributes` 钉死。

它们经 HTTP 原样下发给客户端:`CRLF` 会让 `curl | sh` 报 bad interpreter。
而 `install.ps1` 还必须保持**纯 ASCII** —— PowerShell 5.1 在中文系统按 GBK 解码,
会把中文注释里的字节吃进相邻引号,脚本直接语法错误。

可执行位也要注意:`deploy.sh` 在 Windows 上编辑后 git 里会变成 644,
`./deploy.sh` 就 permission denied(看起来像脚本坏了)。用
`git update-index --chmod=+x <file>` 单独提交。

## G. 文件托管(客户端取二进制的唯一入口)

### G1. 默认由面板托管,但源可以由装的人显式选

`agent` 与 `frpc` 默认都由面板托管:`/api/agent/bin/{os}/{arch}`、`/api/frpc/bin/{os}/{arch}`。
安装命令里可以显式选来源(`--source git`,Windows 是 `-Source git`),此时命令里的下载地址
直接指向更新源,客户端自己去取。

理由不是"看起来整齐":内网机器往往**能连面板、连不上 GitHub**,所以默认必须是面板;
但反过来的情况同样真实 —— 面板出口带宽是所有客户端共用的(装一台 6.5MB agent,
之后还有 20MB frpc),慢的时候让客户端直接去 CDN 取会快很多。所以给一个明确开关,
而不是让程序去赌。

### G1a. 源列表:有序候选,两个列表

**模型**:一个源就是一个候选(token),形态照搬 Go 的 `GOPROXY` ——
逗号分隔、顺序即优先级、`github` 表示官方直连、前缀则原样写在前面:

```
panel                  经面板中继(仅客户端列表合法)
github                 直连 github.com
https://ghfast.top/    镜像前缀:实际地址 = 前缀 + 官方地址
```

**两个列表,不能合并**:

| 设置项 | 管什么 | 允许 panel |
|---|---|---|
| `server_sources` | 面板自己取 frps / frpc 缓存 / agent 缓存 / 清单 | 否 |
| `client_sources` | 客户端取 frpc / 自动更新(安装包固定走面板) | 是 |

分成两份的原因:面板那台机器和客户端那台机器的网络是两件事,一份列表说不清 ->
内网面板 + 公网客户端、或反过来,都是真实场景。

**列表长度不设上限**。曾经有过一条"最多 4 个"的硬限制,理由是"每多一个都要多等一轮
超时"。但它拦的是用户自己排的回退链:manual 下多一项的代价是**零**(前面成功了就不往下走),
auto 下只是多测一次、多几秒,而用户能在记录里看到。更糟的是它报错的位置:
刚加完第五个源、点测速时直接 400,用户分不清是"限制"还是"配置写错了"。
**代价要在界面上说清,不要设卡。**

**都随配置每轮下发**,改设置下一轮心跳生效、不用重装。写进 systemd unit 是错的 ——
面板换了源之后,已装机器会继续用旧地址。

### G1b. 前缀只对 github.com 地址生效

规则收在 `shared.Source.Apply` 里,**只此一处**,不要在各调用点再写一遍。
理由:ghproxy 那类是在原地址前面再套一层代理,自建更新源套上去必然 404。

`mirror_base` 是被淘汰的单值字段,现在由 `syncMirrorBase()` 从列表派生 ——
保留它只为两件事:老版本客户端(≤0.7.13)只认它,以及「文件与更新」页还在读。

### G1b2. 策略:手动 / 自动择优(`source_mode`)

`auto` 时**每次真要下载前**临时测候选源并排序,`manual` 时严格按列表。
默认 `manual` —— 升级后"什么都没变"比"变快了一点但说不清"重要。

三条不能省的性质:

1. **测两轮,不是一轮**。一轮只能得到"某一瞬间多快";两轮才有抖动。
   抖动的源必须降级否则"峰值 500KB/s、下到一半掉到 20KB/s"会被排到第一,
   用户会认为测速是假的。见 `shared.scoreProbe`。
2. **测的是待会儿真下的那个地址**,不是 healthz。轻接口人人 5ms,
   区分不出"下载 20MB 时谁会卡"。客户端有**两类**下载,地址各不相同:
   取 frpc 走 `/api/frpc/bin/<os>/<arch>` + frp 发布包,自更新走
   `/api/agent/bin/<os>/<arch>` + `frpeasy-agent-<os>-<arch>`。
   探测地址由 `downloadTarget` 决定(`frpcTarget` / `agentTarget`),
   不许写死 —— 写死成 agent 的路径会让"取 frpc"测的是另一条通道。
3. **客户端自己测**。面板只能测自己那台机器到镜像的链路;
   客户端可能在完全不同的网络里。所以 auto 下发的是"候选集合 + 你要自己测",
   不是"我替你排好的顺序"。客户端侧的排优结果与每次下载都上报
   (`POST /api/agent/source-event`),否则出问题时最关键的一半信息永远缺失。

**两侧都能手动测,但含义不同**(`POST /api/sources/probe` 的 `side`):

- `side=server`:测面板自己那台机器 → 可以按实测重排这张列表(写库)。
- `side=client`:测面板到该前缀的链路 →**只回答「前缀能不能把文件取下来」**
  (最常见的失败是 404 / TLS 错,都是前缀拼错),**不重排**、不写库,
  返回里带 `caveat` 说明"速度不代表客户端"。
  曾经这里直接 400 拒绝("面板测不到客户端网络")——技术上没错,但用户加了个前缀
  想验证能不能用,却只得到一句拒绝;而"前缀是死的"面板恰好查得出来。
  **能查的部分要查,查不了的部分要说清楚。**
  列表里的 `panel` 那段没有可测地址,标 `skipped`(界面显示"不用测"),
  不能伪装成 0KB/s 或"不可用"。

排优结果缓存 `rankTTL`(10 分钟),key = 侧 + 列表签名(+客户端侧: 面板路径与
本次文件的标识)。换文件就换签名 —— 拿 frpc 的测速结果指导自更新是用错数据。

**测速结果必须被使用**。只展示不排序等于没做 —— 「测速并按结果重排」与自动择优
走的是同一个 `OrderByProbe`,不许出现"界面测出来的顺序"和"实际尝试顺序"不一致。

### G1c. 允许回退,但回退必须可见

1. 每次失败进 `lastNote`,随心跳上报(`bin_source` / `bin_note`),客户端卡片显示
   「二进制来源: 面板中继/ghfast.top(已回退,悬停看原因)」。
2. 错误信息列出**所有**尝试过的源与各自原因,不是只报最后一条。
3. 服务端也一样:日志里逐条打印,最终错误汇总所有源(`panel.sources.go` 的 `trySources`)。

### G1d. 其余三条边界

1. **版本与内容始终由面板决定**。源只决定"从哪儿取这个文件"。一旦客户端能自己
   决定版本,面板下发的端口和配置就会和客户端跑的 frpc 对不上。
   自更新同理:面板下发 `url` 与 `url_git`,版本与 sha256 都来自面板,客户端只挑地址,
   每个地址都要独立走完下载 + 校验(`fetchVerified`)。
2. **frp 的资产地址能拼就不查 API**(`shared.FRPAssetURL`)。发布路径是固定的
   (`.../releases/download/v<ver>/frp_<ver>_<os>_<arch>.tar.gz`),而 `api.github.com`
   在国内经常连不上 —— 镜像能代理下载却代理不了 API,为了解析 latest 去查 API
   等于把整个源作废。面板先把 latest 换成缓存里的具体版本(`concreteFRPVersion`)。
3. **安装那一步固定经面板**,不按源列表走:装的时候 agent 还没跑起来、列表还没下发,
   而且装不上比走慢一点的通道严重得多。`--source` / `-GitBase` 仍被脚本接受但忽略
   (老命令里有),别把它们加回生成器。

## H. 配置的保存与不可静默丢失

### H1. 保存设置只提交真正改动过的字段

设置页是**全站唯一**提交多个字段的地方(其余页面都只提交单个 key)。原来它把整份
表单原样回传,后果是:表单里任何一个字段状态不对(设置还没加载完、输入被冲掉、
页面跑的是旧 bundle),保存就会把库里那一项覆盖成空 —— 用户看到的就是
「面板更新后配置消失了」,而且完全看不出是哪一步弄丢的。

现在 `save()` 逐字段比对 `settings` 里的当前值,只把改动项放进 body。
**新增任何设置字段都要加进这个比对**,不要再退回"一次性回传整份表单"。

### H2. 表单只在第一次拿到设置时回填

`useEffect` 依赖 `[settings]` 是不够的 —— store 每次 `loadSettings()` 都会
`setData({...d, settings: r})` 放一个**新对象**,引用每次都变,于是表单被反复
重置,用户正在输入的值被冲回原值。必须用 `hydrated` 这类标记保证只灌一次。

「放弃修改」也不能只重新 `loadSettings`,要用当前 settings 直接重灌表单,
否则会被 hydrated 挡住、点了没反应。

### H3. 「有值 → 空值」必须显式要求

服务端对 `public_addr` 的护栏:空值只有在请求带 `clear_public_addr=1` 时才写入,
否则整条字段被忽略并记日志。任何"空表单式"的整体提交都清不掉它。

端口类字段(`frps_bind_port` / `dashboard_port` / `port_range_*`)必须是
1–65535 的整数,空串/非数字直接 400 并**点出字段名**。这些值会拼进 frps 的 toml,
写进库之后 frps 起不来,而报错来自子进程日志,用户根本联想不到是设置项。
端口池还要按「保存后的最终值」做组合校验(start < end),单看每一项合法、
组合起来倒置是最常见的输入错误。

### H4. 每次设置变更都要留一行审计日志

`[settings] 已变更: portrait_addr, frps_bind_port` —— **只记 key 名,绝不记值**
(令牌、口令都经过这个接口)。有了它,「配置自己没了」这类反馈才有答案:

```bash
journalctl -u frpeasy | grep '\[settings\]'
```

配置本体在 `<数据目录>/frpeasy.db`(SQLite)。面板自更新只替换二进制、沿用同一个
`--data`,升级不会动这个文件;真丢了只有两种可能:某个请求把它写成了空
(现在被 H1/H3 挡住),或者换了数据目录(查 `systemctl cat frpeasy` 里的 `--data`)。

### H5. 界面上的动作,输入必须是界面上的当前值

按钮旁边的列表/输入框里是**用户正在看着的东西**,它可能还没保存。任何"就地
处理这份东西"的动作(测速重排、批量检查、预览、派生)都必须把当前值一起提交,
服务端以请求为准、库里那份只做兜底;返回结果**只能覆盖同一个集合**,不能拿来
覆盖整份表单。

反例(0.7.22 的真实缺陷):「测速并按结果重排」只发 `{side,apply}`,服务端读库里
的 `server_sources`。用户点「+ ghfast」再点测速 → 只测了库里那一项,再拿结果
`setServerSources(order)` —— 刚加的源当场消失,用户看到的是「只测了一个源」。

同一类的还有两种"点了没反应也不报错",都属于必须消灭的静默失败:

- 输入不合法就 `return`(自定义前缀缺 `https://`):要么禁用按钮,要么给出原因。
- 服务端静默丢弃一项(`SourcesForPanel` 会过滤 `panel`):界面显示两项、实际
  按一项工作。校验只做一次、**两处用同一个判断**,丢掉就报错。

判断"这个动作用的是哪份数据",只需问一句:它读的是**我正在看的**,还是
**库里上次保存的**?后者一律要改成前者。

### H6. 切页面不能丢掉「我正在编辑的东西」

SPA 切页会卸载组件,所有 `useState` 一起消失。设置页的输入是"一次性工作"
(加个源 → 去别的页面看一眼 → 回来继续),卸载即清空的表现是
「我刚加的项没了」「刚才测出来的数据没了」,而且**没有任何提示**。

两层都要留住:

1. **表单草稿**:模块作用域一个 `draft`,每次改动写入,挂载时优先取它
   (有草稿就把 `hydrated` 初始化为 true,别被库里的值再冲一遍)。
   草稿**不写库**——要不要落库仍然只由「保存」决定。
2. **测出来但没存的结果**:逐项探测结果放在服务端的 rank 缓存里
   (`/api/sources/events` 的 `last_rank`),挂载时铺回列表行;
   过期也照样铺,块上标「已超过 10 分钟」。

同理,任何"一次操作产生的中间结果"都不该只活在组件状态里:
要么进 URL、要么进 store、要么进服务端,否则切一次页面就等于没做过。

## I. 安装/卸载与平台边界

### I1. 只有面板碰 Git,客户端一律从面板取

除面板本体(deploy.sh 从 Release 装)以外,**任何客户端二进制都只从面板下载**:

| 文件 | 面板怎么拿到 | 客户端从哪取 |
|---|---|---|
| frps | 按 `frp_version` + 镜像从上游拉,缓存 `<data>/bin` | 不用(面板自己跑) |
| frpc | 首次被请求时拉,校验后缓存 | `GET /api/frpc/bin/<os>/<arch>` |
| agent | 同上 | `GET /api/agent/bin/<os>/<arch>` |
| 安装脚本 | 内嵌在二进制里 | `/install`、`/install.ps1` |

**frpc 曾经有一条「面板取不到就直连 GitHub」的回退,已删除。** 那条路让客户端绕过面板,
面板上配的镜像变成摆设,内网机器上表现为「有时通有时不通」,而日志里看不出走了哪条。
现在取不到就明确失败,错误信息直接指向「文件与更新」页的预存按钮。

### I2. 本机执行卸载必须向面板报备

两条卸载路径(面板云端下发 / 在那台机器上跑卸载命令)最终都会让 agent 从面板视野里消失。
**如果不报备,面板只能看到「心跳停了」——「被卸载」和「关机了」在数据上完全一样**,
记录会一直挂着,用户没法判断该不该清。

- 云端下发:心跳带回 `uninstall:true`,由 `ConsumeAgentUninstall` 写 `uninstall_sent_at`。
- 本机执行:agent 删自己之前调 `POST /api/agent/goodbye`(凭据同心跳),
  `MarkAgentLocalUninstall` 写 `uninstall_sent_at` + `uninstall_by_local=1`,
  界面显示成「已卸载(**本机执行**)」,与面板下发区分开。

`install.sh --uninstall` 靠 `agent --goodbye --data <dir>` 完成报备 —— 脚本不解析
`agent.state` 里的 JSON。面板不可达时报备失败、卸载照做(删自己优先级更高)。

**`agent.state` 里必须存面板地址**:卸载时不会带 `--server`,只能靠注册时记下的这个。
老版本 state 没有该字段时报备静默跳过,不报错。

### I3. Android 只有一个入口,且没有「安装」

Android 上的 agent **不注册任何自启、不挂看护循环**,只是把二进制放下去跑一次:

- 不写 `/data/adb/service.d`、不碰 Magisk/KernelSU/APatch/adb su 的任何目录。
  这些方案的目录各不相同,系统版本差异又大,**猜错轻则静默无效,重则设备起不来**。
- 面板**不提供**「adb 版 / root 版」两条命令。`--elevate` 的语义是「以 root 身份运行」,
  不是「root 安装」;要提权的人自己在命令后加,脚本会依次试 `su -c` / `su 0` / `su root -c`,
  拿到 uid 0 才算成功。
- 探测本机服务读 `/proc/net/tcp`、转发端口都不需要 root,所以默认命令不带 `--elevate`。

### I4. 卸载要清缓存,`--keep-data` 只留数据库

- 面板默认卸载:删 unit、停进程、清 frp 孤儿、删 data(含 `<data>/bin` 里的 frps/frpc/agent
  缓存,40MB+)、删程序目录。
- `--keep-data`:只保留 `frpeasy.db*`。`bin/` 是二进制缓存、`update/` 是自更新临时文件、
  `*.log` 是日志 —— 全部可重建,留着只是白占空间。「保留配置」就该只保留配置。
- 客户端卸载:删自启、二进制、整个数据目录(含 frpc 缓存与 `agent.state`)。
